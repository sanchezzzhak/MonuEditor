# Monu Editor — концепция интерфейса

**Статус:** проектное предложение  
**Область:** MonuEditor  
**Связанные проекты:** MonuEngine и MonuGame  
**Назначение документа:** зафиксировать направление интерфейса и использовать визуальные ориентиры при дальнейшей разработке.

---

## 1. Основная идея

Monu Editor уже оформлен в духе Unreal Engine 5. Это направление разумно сохранить: разработчику не придётся переучиваться на необычную модель редактора, а основные рабочие процессы будут узнаваемыми.

При этом Monu не должен становиться копией Unreal. Нужен собственный интерфейс, который:
- объединяет удобную редакторскую компоновку с архитектурой Rust + Bevy ECS;
- не скрывает техническую структуру проекта;
- позволяет работать как через визуальные инструменты, так и напрямую через Rust;
- расширяется плагинами без необходимости менять ядро редактора;
- адаптируется под разные задачи через рабочие пространства.

**Ключевой принцип:** редактор помогает работать с движком, но не является обязательным способом разработки. Проект должен оставаться полноценным Rust-проектом.

## 2. Базовая компоновка

Основное окно редактора целесообразно строить из следующих зон.

### Верхняя панель
- меню проекта и редактора;
- команды сохранения, отмены и повтора;
- запуск, пауза и остановка игры;
- выбор целевой платформы и конфигурации запуска;
- переключение рабочего пространства;
- доступ к настройкам, поиску команд и документации.

### Центральная область — рабочая поверхность
В зависимости от активного инструмента это может быть:
- 3D Viewport сцены;
- Terrain Viewport;
- Blueprint Graph;
- Material Graph;
- Animation Timeline;
- UI Designer;
- Sequencer;
- редактор генераторов.

Рабочая поверхность должна поддерживать вкладки и несколько открытых документов.

### Outliner / Hierarchy
Иерархия объектов и сущностей текущей сцены:
- поиск и фильтрация;
- группировка и папки;
- видимость и блокировка;
- выбор нескольких элементов;
- фильтры по типам и компонентам;
- контекстные действия;
- отображение связей и вложенности.

Для ECS важно не маскировать модель данных под классическую объектную иерархию. Outliner показывает удобное представление сцены, а отдельные инструменты должны позволять изучать Entity и Components напрямую.

### Details / Inspector
Контекстная панель выбранного объекта или ресурса:
- свойства Transform;
- компоненты ECS;
- параметры выбранного инструмента;
- ссылки на ресурсы;
- диагностические предупреждения;
- пользовательские свойства и редакторы компонентов.

Компоненты должны регистрировать собственные инспекторы. Плагины могут добавлять свои типы полей и редакторы.

### Content Browser / Asset Browser
Работа с обычными файлами проекта:
- папки и коллекции;
- поиск, фильтры и теги;
- превью ресурсов;
- импорт и повторный импорт;
- зависимости и ссылки;
- статусы Asset Pipeline;
- контекстные действия и drag-and-drop.

Исходные файлы остаются доступными во внешних приложениях. Asset Browser не должен превращать проект в закрытую базу данных.

### Нижняя панель
Вкладки, которые можно закреплять или скрывать:
- Output / Console;
- Build;
- Problems;
- Profiler;
- Debugger;
- Asset Import;
- Event Log;
- Search Results.

Панель не должна занимать постоянное место, если не нужна текущей задаче.

## 3. Рабочие пространства

Рабочее пространство — сохранённая конфигурация панелей, вкладок, инструментов и их расположения. Оно не должно быть отдельным режимом движка или ограничивать доступ к функциям.

Предлагаемые стартовые пространства:

| Workspace | Основная компоновка |
|---|---|
| Level | Viewport, Outliner, Details, Content Browser |
| Terrain | Terrain Viewport, инструменты кистей, слои, маски, биомы |
| Blueprint | Graph, список графов/переменных, Details, Debug |
| Materials | Material Graph, Preview, параметры, ресурсы |
| Animation | Preview, Timeline, Skeleton/Hierarchy, Curves |
| VFX | Niagara-подобная рабочая область частиц, граф, Preview, параметры |
| UI | UI Canvas, Widget Tree, Details, Preview |
| Cinematic | Sequencer/Timeline, Viewport, Camera, Tracks |
| World | Streaming/Chunks, World Outliner, LOD и диагностика |
| Profiling | CPU/GPU, ECS, Rendering, Physics, Streaming, Timeline |

Это стартовые пресеты, а не закрытый перечень. Пользователь должен иметь возможность создать собственное пространство.

## 4. Настраиваемость

Обязательные возможности:
- dockable panels;
- вкладки и разделение областей;
- перемещение, закрепление и изменение размеров панелей;
- сохранение нескольких раскладок;
- восстановление стандартной раскладки;
- несколько мониторов и отдельных окон;
- контекстные меню;
- настраиваемые панели инструментов;
- переназначение горячих клавиш;
- поиск команд по названию;
- сохранение раскладок в проекте или профиле пользователя.

Нужно предусмотреть защиту от потери интерфейса: команда Reset Workspace должна быть доступна независимо от текущей раскладки.

## 5. Связь с Rust и Bevy ECS

Визуальные инструменты должны быть интерфейсом над реальными системами движка, а не параллельной имитацией.

### ECS Inspector
- просмотр Entity и её компонентов;
- добавление и удаление компонентов;
- редактирование отражаемых полей;
- просмотр связей и событий;
- поиск по Entity ID и типу компонента;
- отображение источника данных и ошибок.

### Rust API
- регистрация собственных типов и редакторов;
- описание отображаемых полей через Reflection/метаданные;
- возможность предоставить специализированный Inspector;
- доступ к контексту проекта и активной сцены через публичный API редактора.

### Blueprint
Blueprint — визуальный способ авторинга игровой логики для тех, кому так удобнее. Это не эмуляция Rust и не замена основному Rust API.
- визуальные графы событий, функций и логики;
- входы, выходы, переменные и типы;
- пользовательские узлы из Rust;
- отладка выполнения и просмотр значений;
- возможность связывать Blueprint с пользовательскими Rust-классами/типами согласно принятой модели наследования.

## 6. Плагины и пользовательские панели

Plugin API должен позволять добавлять:
- новые панели и окна;
- вкладки и рабочие пространства;
- инструменты Viewport;
- контекстные меню и toolbar actions;
- пользовательские типы ресурсов и их редакторы;
- ECS Inspector для собственных компонентов;
- Blueprint nodes;
- команды, горячие клавиши и настройки.

Плагин не должен требовать изменения исходников MonuEditor. При отключении плагина редактор должен корректно обработать отсутствующие панели и неизвестные типы ресурсов, не повреждая проект.

## 7. Viewport и взаимодействие со сценой

Viewport — центральная рабочая область уровня.

Базовые инструменты:
- Select, Move, Rotate, Scale;
- локальные и мировые координаты;
- snapping по сетке, углам и поверхности;
- pivot и transform gizmos;
- несколько режимов отображения;
- камеры и bookmarks;
- изоляция выбранного объекта;
- отображение коллизий, навигации, bounds и диагностических слоёв;
- инструменты измерения;
- undo/redo для редакторских операций.

Инструменты Terrain, Foliage, Water, Road и Generator должны встраиваться в общий Viewport, сохраняя единые принципы навигации и управления.

## 8. UX-правила

1. **Контекстность.** Показывать параметры выбранного инструмента или объекта, не перегружая все панели сразу.
2. **Непрерывность.** Переключение Workspace не должно закрывать документы или терять состояние.
3. **Обратимость.** Редакторские изменения должны поддерживать Undo/Redo там, где это технически возможно.
4. **Ясные статусы.** Импорт, сборка, компиляция шейдеров и сохранение показывают прогресс и ошибки.
5. **Поиск.** Команды, ресурсы, Entity и настройки должны быстро находиться через поиск.
6. **Расширяемость.** Панели ядра и панели плагинов используют согласованные правила поведения.
7. **Производительность.** Тяжёлые операции выполняются асинхронно; интерфейс не должен зависать во время импорта, сборки или генерации.
8. **Доступность.** Масштабирование UI, понятные состояния фокуса, настройка горячих клавиш и поддержка локализации.

## 9. Визуальное направление

Рекомендуется сохранить тёмную рабочую тему с аккуратным бирюзовым/голубым акцентом, но закрепить её собственной дизайн-системой Monu.

Нужно определить:
- типографическую шкалу;
- размеры и отступы;
- систему иконок;
- цвета состояний: normal, hover, selected, disabled, warning, error, success;
- оформление вкладок, доков, деревьев и инспекторов;
- правила плотности интерфейса;
- светлую тему как возможное дополнение, не как обязательную задачу первого этапа.

Цвет не должен быть единственным способом передачи состояния. Для ошибок и предупреждений нужны иконка и текст.

## 10. Визуальные референсы

В `images/monu-editor-concept-overview.png` приложен концептуальный лист из трёх экранов:

1. **Level Workspace** — 3D Viewport, Outliner, Details и Content Browser.
2. **Terrain Workspace** — кисти, слои, heightmap, masks, биомы и настройки растительности.
3. **Blueprint Editor** — граф логики, список переменных, параметры узлов и отладка.

Это не снимки существующей версии MonuEditor и не точная копия интерфейса другого движка. Это визуальная гипотеза, которая помогает обсуждать расположение инструментов и общую плотность интерфейса. Текст на изображении может быть условным; источником требований является этот документ.

## 11. Этапы реализации

### Этап A — основа редактора
- система панелей и docking;
- вкладки и несколько документов;
- сохранение раскладок;
- базовый Level Workspace;
- Viewport, Outliner, Details, Content Browser;
- Command Search и горячие клавиши;
- Output/Console.

### Этап B — специализированные пространства
- Terrain Workspace;
- Blueprint Workspace;
- Material Workspace;
- Animation Workspace;
- Profiler и Debugger;
- расширенные инспекторы компонентов.

### Этап C — расширяемость
- публичный Plugin API для панелей и инструментов;
- пользовательские Workspace;
- пользовательские редакторы ресурсов;
- дополнительные окна и несколько мониторов;
- API контекстных меню и команд.

### Этап D — полировка
- UX-аудит;
- производительность UI;
- масштабирование и локализация;
- доступность;
- улучшение поиска и навигации;
- документация и примеры для авторов плагинов.

## 12. Что не следует делать

- Не превращать редактор в обязательную среду разработки.
- Не прятать Rust и ECS за искусственной объектной моделью.
- Не делать один огромный экран с постоянно открытыми всеми инструментами.
- Не зашивать рабочие пространства в код без возможности расширения.
- Не создавать закрытый формат хранения ресурсов вместо обычных файлов.
- Не пытаться реализовать все специализированные редакторы до появления надёжной основы docking, команд и API панелей.

---

## Итог

Monu Editor должен ощущаться как полноценный профессиональный редактор уровня UE5 по удобству и организации рабочего процесса, но оставаться самостоятельным инструментом для Rust + Bevy ECS. Самая важная инвестиция на раннем этапе — не десятки отдельных окон, а надёжная модульная система панелей, Workspace, команд, инспекторов и Plugin API. На ней затем можно последовательно строить Terrain, Blueprint, Materials, Animation, VFX и остальные инструменты.
